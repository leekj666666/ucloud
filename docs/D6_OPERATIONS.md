## 恢复原则

1. 先检查控制器和诊断容器是否仍在运行。一次模型请求可能需要较长时间，不能仅凭暂时没有日志就判定卡死。
2. 若基础设施确实中断，保留原日志、结果和调度状态；控制器应暂停，不自动重跑不确定任务。
3. 恢复既有基础服务，核查 Kubernetes API、两个 namespace、验证器证据挂载和模型代理。不得重建健康基线、清空业务数据或工厂重置 Docker。
4. 精确遗留故障可运行 `PYTHONPATH=backend:. .venv/bin/python -m benchmarks.d6.recover <episode_id>`。它只恢复评测器拥有的字段，并校验 UID 和当前值。此操作不计 Agent 修复。
5. 在两个 namespace 的独立业务校验都通过、无活动 fixture、原账本无在途请求、冻结协议校验通过后，才能显式关联不确定任务到原始结果。需要保存关联审计；禁止直接把任务改为成功。
6. 环境无效的原始尝试保留在主结果中；如补测，用新 ID 与原尝试关联，单列补测结果，不按成功与否挑选。

Docker/WSL 重启可能导致旧容器的绑定挂载不可写。曾出现第二验证器业务检查全部通过，但归档报 `PermissionError`；应以相同镜像、身份和精确目录重新挂载验证器，再确认归档与清理均通过。不要绕过证据归档门槛。

模型代理恢复时先确认实际账本。早期恢复脚本固定 batch4，轮换到 batch5 或更高后不能直接调用，以免错误回退账本。真实 Key 只保留于宿主代理，诊断容器使用受限代理令牌；日志和文档中不得输出凭据。

## 运行期间的变更边界

协议每项任务都核对产品、评测 Python、锁文件、镜像、模型和基线。正式留出开启后，若必须修改这些内容，应暂停、建立新版本并说明已查看数据，不能继续声称同一份未见测试。运行说明和只读结果汇总可以完善，但不得改写原始判定。

正式试验与生产控制台、清洁部署的实机故障测试串行执行，避免共同业务图干扰和内存竞争。评测期间不要手动注入故障或启动生产 worker。保持 Windows、WSL 和 Docker 运行；当前控制器不是开机自启服务。

## 有限后续流程

主调度正常终结后，本轮交付辅助流程对已明确关联的环境中断各运行一次新 ID 补测，并单列汇总。它核对原始结果 SHA-256，不替换主结果、不重试普通模型失败，也不把任意失败都归因于环境。不确定补测必须显式核对，不能重复发送请求。

辅助流程在主控制器提前退出时暂停，不能自动处理未知物理现场；不会自动部署第二集群、代替用户试用或宣告 D6 完成。辅助脚本保存在 D 盘交付资料中，与冻结产品/评测源码分开记录哈希；其 8 项隔离安全测试不并入冻结 CI 的 256 项。
