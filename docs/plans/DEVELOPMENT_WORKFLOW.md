# 云巡：开发流程与优化验证执行方案

日期：2026-10-23。依据 SRE_AGENT_PROJECT_PLAN.md 与 ENVIRONMENT_STATUS.md。此文件明确接下来的执行顺序，不代表业务代码已完成。

## 一、起点和完成定义

现有：WSL/Docker/kind、Python/Node、独立 HolmesGPT 环境、数据库和监控服务、DeepSeek 普通请求和真实只读工具往返验收。
缺少：HolmesGPT 完整引擎联调、被测业务、自动遥测、事件编排、处置、业务验证、控制台与评测。

最终交付必须能现场执行：注入故障 → 告警 → 动态调查 → 证据支持的处置 → 真实执行 → 独立业务验证 → 报告。支持失败、中断、拒绝处置和转人工路径。

功能完整性、可靠性和真实收益为第一要求。开源已有思想可以采用并标明归属；通过测试证明改进效果，不为追求新颖而增加无收益模块。

## 三、实现约定

- 主开发目录固定为 WSL /home/lee/sre-project（物理在 D 盘）；D:/uclaude 保存计划、报告和安装记录。避免维护两份独立源码。环境清单的 Windows 副本属于快照，正式锁文件以主仓库为准。
- 核心模块：api、worker、diagnosis、tools、executor、verifier、demo-app、frontend、evaluation、deploy。数据库存 Incident、Evidence、Hypothesis、ActionPlan、ActionAttempt、Verification、Usage。
- HolmesGPT 使用独立进程/服务适配，避免其依赖与自有后端冲突。D0 验证结果决定采用服务 API 或受控子进程，不提前强行固定未验证接口。
- 编排状态与操作策略由代码保证，模型负责调查与方案建议。日志/检索内容不能改变工具权限。
- 无模型参与的独立验收器始终存在；即使消融业务验证模块，评测端依然保留完整标准。
- 初期 Compose 运行基础设施、kind 运行被测业务；正式交付提供可复现应用部署说明，明确两者网络地址、凭据与资源边界。
- 16GB 主机、WSL 4GB 下串行跑实验。先测内存峰值/OOM/交换空间，再决定调整资源；多 Agent 不同时加载本地大模型。

## 四、候选改进及可证伪假设

这些是工程创新/优化候选，不是经过查新认证的原创算法。论文已有机制注明借鉴来源；参赛主张只覆盖实测支持的范围。

| 编号 | 候选 | 要解决的问题/假设 | 受控比较 | 关键指标与采用条件 |
|---|---|---|---|---|
| H1 | 变更感知与反证检查 | 最近发布不一定致因；结合变更范围与运行证据减少误回滚 | 相同信息权限；完整机制 vs 不做显式关联/反证的基础诊断 | 发布故障定位、非发布错误回滚；不能仅提高发布子集分数 |
| H2 | 业务不变量验证反馈 | 容器健康可能掩盖下单/库存错误；反馈能促使继续处理 | 仅基础健康反馈 vs 业务验证反馈，外部评分始终完整 | 假成功、业务恢复率、增加耗时；只改善评分检查不算恢复能力提升 |
| H3 | 有界执行与失败补偿 | 错误或无效修复可能扩大影响 | 固定动作集上，基本执行 vs 前置检查+执行后检查+可补偿撤销 | 错误变更、恢复成功、转人工；限定演练环境，无需真实危险操作 |
| H4 | 证据预算与渐进查询 | 大量日志干扰并增加 token | 原始有界查询 vs 过滤/摘要/证据索引 | 成功率、遗漏证据、token、P95；成功率明显退化则不采用 |
| H5 | 规则与模型协作 | 明确 Kubernetes 错误不必反复推理 | HolmesGPT 基础流程 vs 规则预诊断辅助 | 调用次数、时间、恢复率；防止规则直接暴露场景答案 |
| H6 | 已验证 SOP/案例检索 | 重复问题可以复用经验 | 无检索 vs 版本化检索 | 已知变体收益、未知问题误导率；只使用开发集验证的案例 |
| H7 | 职责分工 | 独立审查可能降低错误，也可能只增加成本 | 单诊断引擎 vs 诊断+独立审查；执行/验证程序一致 | 单位成功成本、错误处置、延迟；不预设多 Agent 更优 |
| H8 | 动态预算与模型路由 | 简单任务快速处理，困难任务追加预算 | 固定预算 vs 动态预算，模型和费用披露 | 成功率—成本曲线、超时；先单模型预算优化，再评估其他模型 |
| H9 | 缓存、并行查询与告警合并 | 重复查询及重复事件浪费资源 | 独立任务和告警风暴分别比较 | 时延、重复动作、过期证据；变更后缓存失效 |

优先顺序：H1/H2/H4；H3 中必要执行保护直接作为基础工程实现，额外策略再做消融；H5/H6 次之；H7–H9 依照瓶颈和剩余时间选择。P2 沙箱预演、灰度、补丁生成、多集群仍保留在总计划候选池，不阻塞核心交付。

## 五、实验设计

### 基线

- B0 固定规则/脚本：在其明确覆盖范围内评测，同时报告全体适用任务覆盖率。
- B1 同模型单次分析：比较诊断；若需要恢复对照，使用共同执行器处理其结构化计划，并标明这是我们的基线包装。
- B2 固定版本 HolmesGPT 基础配置：在相同观测权限下比较诊断。端到端比较时明确共同执行器/验证器，不把缺失执行功能简单记为失败。
- B3 我们的完整方案：相对 B2 的增量来自可列举模块，不通过不同模型或额外答案制造优势。

### 数据

先建设 12 个开发案例、8 个验证案例、至少 20 个最终测试案例。案例需包含故障实体、原因、发布关系、影响、可接受动作、禁止动作、复原方法、业务判定条件。测试覆盖发布回归、非发布异常、无关发布干扰、表面恢复、工具失败、不能自主处理的任务。

开发/验证按故障配置、注入机制和业务变体划分，避免仅改名称形成伪独立。标准答案、注入与参考修复不进入 Agent 的文件系统、工具返回或检索库。无法做到独立第三方盲测时，明确称为留出配置测试。

### 执行

每个正式案例重复 3 次，至少 60 次/端到端方案。三种端到端方案就是至少 180 次，不把 60 次当成所有基线总量。优化筛查先用开发/验证集，减少无效 API 花费。

固定版本、模型模式、预算、负载、权限和环境；随机化方案运行顺序；每次确认健康基线、注入故障、确认故障确实发生，结束后独立复原。模型单轮 tokens 与累计上下文分别记录。

若基础设施导致任务无效，保留记录并按预先定义规则重跑；业务失败和 Agent 超时不能当作环境问题丢弃。记录 start/end、全部工具参数、脱敏结果、动作、模型用量和评分。

### 指标与解释

主指标：业务恢复成功率、错误处置/错误回滚率。辅助：根因准确率、假成功、转人工率、中位数/P95 恢复时间、调用数、token 和单位成功任务成本。

正确转人工单独统计为处置正确，不计为自主恢复。诊断与缓解、永久修复分别报告。所有方案使用同一个外部验证器：真实业务写入、库存/幂等不变量和持续负载窗口。

小样本先报成功次数/总数、配对胜负及波动，必要时按故障案例聚类估计区间；同一案例三次运行不能伪装为三种独立故障。20 例不能支撑泛化到所有生产故障的结论。

### 优化采纳

在验证集上一次改一个因素，再比较最佳少量组合及逐项移除。提前约定约束：禁止动作 0；外部验证器无已知假阳性；优先提高恢复率且不提高错误处置。成本优化初筛可用降低约 20% 作为有意义候选，但必须说明样本波动和效果取舍，不机械凑阈值。

冻结最终方案后运行留出测试，不根据最终测试反复选参数。测试后修复问题则新建版本并重跑受影响及必要全套测试。
