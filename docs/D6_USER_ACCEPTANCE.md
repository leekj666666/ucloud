## 入口与任务

浏览器访问 `http://localhost:28080`，从 `D:/uclaude/clean-console-access.txt` 获取本机访问码。访问码不是模型 Key，不要放入截图、录像、仓库或反馈文本。试用使用演练服务和默认逐次人工审批。

| 步骤 | 用户实际操作 | 严格判据 |
|---|---|---|
| 发起调查 | 输入观察到的业务症状，核对服务/namespace | 默认人工审批；不要求用户填写根因、答案或工具命令 |
| 阅读证据 | 查看五阶段闭环、日志/指标/发布和建议动作 | 能区分观测事实、模型判断、待执行动作及未解决问题 |
| 批准 | 对准备好的单个演练方案逐项核对后批准 | 未批准前无变更；批准绑定当前方案与资源版本 |
| 业务验收 | 查看实时业务检查和窗口进度 | 不将 HTTP 健康、告警消退或执行完成直接显示为业务恢复 |
| 拒绝 | 在另一项演练中填写原因并拒绝 | 状态明确为拒绝；未批准的动作未执行，评测清理另记 |
| 停止 | 在另一项演练中发出停止请求 | 请求与确认分开；不再开始新写入；部分窗口不算成功 |
| 导出 | 下载 JSON 和 Markdown 报告 | 状态、证据、审批、动作、验证、用量和限制与页面一致 |

恢复需要完整 120 秒窗口、120 次请求和至少 12 次完整业务检查，全部业务不变量、监控、相关严重告警、资源样本及 P95 门槛通过。暂时等待不是失败，但超时、模型无效、工具不可用必须清楚显示并如实转人工。

## 反馈记录

每次试用记录日期、任务 ID、操作、页面预期、实际结果、是否完成及具体困惑。不记录访问码或模型 Key。用户发现问题后，保存原始记录；若需改产品，按 D6 冻结版本边界另立版本并复验。

需要回答的四项问题：

1. 是否能独立完成发起、批准/拒绝、停止和导出？哪一步需要解释？
2. 是否能看懂为什么建议这次变更、影响哪个资源，以及证据是否充分？
3. 是否能区分已执行、仍在验证、真正恢复和已转人工？
4. 导出报告是否足够用于复盘？是否遗漏关键失败、审批或未知费用？

维护者保存原始反馈和关联结果后再签署本项完成。没有真实用户反馈时保持“未完成”。
