## 失败记录与修正

共保存 7 次开发验收，4 次未完成/失败，最后完整通过。版本和验收器在调试中有变化，不能由此计算正式恢复率。

1. 最初读取健康端点遇到 Pod 更换后的端口转发断连，补有界重连及发布版本确认。
2. 首个失败样本可能是发布切换期 gateway 无法连接订单服务；未将其冒充库存地址错误。
3. Trace 异步到达 Loki，改为持续查询所有已归档失败样本，保留父子关系/错误状态要求与超时上限。
4. Service 路由错误暴露 port-forward 绕过真实路径的验证盲区；增加独立 verifier-api，通过真实 NodePort/Service 重验四种故障。

SDK 记录显示本机某些 DNS 失败调用耗时约6–11秒；这是故障期间的观测值，不宣称 HTTP 客户端单阶段 timeout 等于端到端总时限。后续 D2/D3 仍须落实其执行与验证预算。

另外，最终重复CI曾发现真实业务竞态：确定性订单ID与幂等键同时受唯一约束，但INSERT只处理key冲突，偶发由orders_pkey返回500。现改为处理全部可用唯一约束，并在读回时校验身份；新增确定性冲突反例，真实PG并发用例强化为20轮、每轮4个同步请求。原19通过/1失败CI主日志和当时读取的关键异常摘录保留。该次原始服务日志后来被pytest临时目录清理，不能冒称完整原始服务日志已归档；后续CI已将服务日志与JUnit直接写入持久运行目录。修复语义依据PostgreSQL官方INSERT文档：https://www.postgresql.org/docs/current/sql-insert.html 。

发布快照补入部署器登记的image_content_id、公开配置摘要及镜像内容变化的显式差异；旧版本无法取得摘要时保留未知，不用标签冒充摘要。
